Cogniate for Moodle: importing Cogniate courses into MoodleCloud

How the Cogniate Moodle Plugin, a Cogniate-hosted integration connector and Cogniate's REST APIs work together to bring AI-authored courses into MoodleCloud and self-hosted Moodle sites.

1Executive summary

The goal is to let a Moodle administrator bring courses authored in Cogniate into a Moodle workspace, with MoodleCloud as the primary target, using Cogniate's REST APIs as the source of truth for course content.

MoodleCloud does not allow plugins to be installed

Moodle's own MoodleCloud FAQ states that plugin installation is not permitted on MoodleCloud plans, so that all sites stay simple and stable. Plugins are only possible on Moodle LMS or Moodle Workplace hosted by Moodle or a certified partner, or self-hosted. A design that relies on a plugin alone cannot reach MoodleCloud customers.

This specification therefore keeps the Cogniate Moodle Plugin for sites that allow plugins, and moves the MoodleCloud integration into a Cogniate-hosted Integration connector that uses only features every MoodleCloud site already has: web services, course restore and LTI 1.3 Advantage.

The recommended solution is one transformation engine with three ways into Moodle. All three are driven from the same admin console inside the Cogniate app, and all three use the same course model so a course looks and behaves the same whichever route it takes.

ChannelRuns onWhat the Moodle administrator gets
Package importMoodleCloud, any MoodleA native, editable Moodle course (sections, Page, Book, Quiz, H5P, SCORM) delivered as a backup package built by a real Moodle instance. The admin restores it in one guided step.
Live linkMoodleCloud, any MoodleCogniate registered as an LTI 1.3 Advantage tool. Teachers pick Cogniate modules with Deep Linking; content stays live, updates with Knowledge DNA, and scores return to the Moodle gradebook.
Cogniate Moodle PluginSelf or partner hostedlocal_cogniate adds a catalog, import wizard and automatic sync inside Moodle, with no manual restore step.

The plugin's PHP code is reused inside the connector: a headless Moodle (the Build Runner) runs the plugin to write the course natively and then uses Moodle's own backup engine to produce the package that MoodleCloud restores. That gives MoodleCloud customers the same import quality as plugin customers, from one tested codebase.

Phase 1 (package import plus plugin core) is estimated at ten weeks after a three-week discovery phase that confirms the Cogniate API contract. Live link and automatic sync follow in phases 2 and 3 (section 13).

2Cogniate platform analysis

Cogniate positions itself as an AI-native enterprise course co-authoring platform that takes an organisation from course concept to deployable course in under an hour. Its assistant, Lyra, builds a course either from a prompt describing the audience and goal, or from source material such as SOPs, instructions for use, release notes and long manuals. Lyra produces a course architecture rather than slides: modules, dependencies, prerequisites, assessments and regional variants.

Three platform capabilities matter most for integration. Knowledge DNA links every module to its source, prerequisites and regional variant, so a course updates when its underlying SOP changes. The Rules-Based Governance Engine checks instructional quality, brand language and compliance before anything ships. And omnichannel publishing targets any LMS with SCORM, xAPI or native Cogniate output, plus a marketplace, analytics dashboards, white-label branding and audit data (completion, version history, source traceability).

3MoodleCloud constraints

MoodleCloud is Moodle HQ's ready-to-use hosting for individuals and small organisations. Every site runs the same pre-configured Moodle, which is what makes it cheap and low-maintenance, and also what limits integration options.

ConstraintEvidenceDesign consequence
Custom plugins cannot be installedMoodleCloud FAQ on moodle.comAll MoodleCloud logic must run outside Moodle, in the connector.
All sites share the same features; settings fixed in config.php are not changed on requestMoodle HQ reply on moodle.org forumsRely only on settings an administrator can switch on in the UI.
Web services with the REST protocol are availableMoodle HQ reply on moodle.org forumsUse a token-scoped external service for provisioning, staging and verification. Confirm on the customer's plan during onboarding.
Core web services create courses and categories but have no general function for creating activitiesMoodle core API; noted by third-party integratorsCourse content cannot be written call by call. Deliver content as a backup package or as LTI links.
LTI 1.1 and LTI 1.3 Advantage are supportedMoodleCloud knowledge baseLive link channel with Deep Linking and grade return.
Course backup and restore are core featuresMoodle corePackage import channel. Plan storage and upload limits apply, so large video is streamed rather than packaged.
Sites track a current stable Moodle releaseMoodleCloud practice VerifyBackups restore only into the same or a newer release, so the Build Runner must match or trail the target site's release.

The practical result: a fully hands-off import of native content into MoodleCloud is not possible with core features alone. The design reduces it to one guided restore step per course version, or zero steps when the customer chooses live link.

The three channels are complementary rather than competing. The decision matrix below is what the admin console shows (in plain language) when an administrator connects a site.

Recommended defaults: use package import for compliance and onboarding courses that must be auditable and editable inside Moodle, and live link for courses whose source material changes often. Plugin customers get both behaviours without the manual step.

A fourth, commercial track runs alongside engineering and is not on the critical path: publish local_cogniate in the Moodle Plugins Directory, apply to the Moodle Certified Integrations programme, and open a conversation with the MoodleCloud team about inclusion in their curated plugin set. Nothing in this design depends on that outcome.

5System architecture

Figure 1 shows how the systems connect. Colours match the system chips used throughout this document. Solid lines are requests and API calls; dashed lines are events or file transfers.

How the parts work together

Cogniate platform stays the system of record for content. Authors create and approve courses there; the governance engine decides what is published; the REST API and webhooks expose published versions; the content runtime renders lessons for live-link learners and records xAPI analytics.

Integration connector is the new service. It pulls a published course through the REST API, converts it into a Moodle course model, and then delivers it by the channel the admin chose. For package import it hands the model to the Build Runner, a disposable container running vanilla Moodle at the target release with local_cogniate installed, which writes the course natively and backs it up to .mbz. For live link it acts as the LTI 1.3 tool that MoodleCloud launches. It also serves the Integration API that plugin sites call.

MoodleCloud needs nothing beyond standard administration: an external service and token for the connector, an External tool registration for live link, and the Restore page for packages.

Self-hosted Moodle runs the Cogniate Moodle Plugin, which fetches the same Moodle course model from the Integration API and writes it with core APIs, so no restore step is needed.

Architecture decisions

RefDecisionRationale
AD-1The connector is a Cogniate-hosted, multi-tenant service, not customer-hosted software.MoodleCloud customers have no servers. A hosted service also lets mapping fixes ship without customer upgrades.
AD-2Backup packages are produced by real Moodle (the Build Runner), never hand-assembled.The .mbz format is internal and changes between releases. Moodle's own backup engine guarantees a package that restores correctly.
AD-3Mapping logic lives in the connector; the plugin is a thin writer that consumes the Moodle course model.One transformation for every channel. Plugin releases are slow to reach customer sites, so keeping logic server-side reduces version drift.
AD-4The plugin's writer code is the same code the Build Runner executes.Package import and plugin import produce identical courses, tested once.
AD-5A canonical Moodle course model sits between Cogniate and Moodle.Isolates Cogniate API changes from Moodle writers and leaves room for future targets such as IMS Common Cartridge for other LMSs.
AD-6Webhooks are treated as hints; scheduled reconciliation guarantees convergence.Webhooks can be lost or blocked by customer firewalls. An updated_since pull closes the gap.
AD-7Sync never deletes learner-facing items; it hides and versions them.Protects quiz attempts, grades and audit evidence.

6.2 Cogniate Moodle Plugin (local_cogniate)

A local plugin is the right plugin type: it adds site-wide integration behaviour without being an activity itself. It installs on self-hosted Moodle, Moodle Official Hosting and partner-hosted sites, and is also the code the Build Runner runs. It never calls Cogniate directly; it talks to the connector's Integration API with credentials issued when the admin connects the site in the console.

6.3 Course Transformer and the Moodle course model

The transformer is the single place where Cogniate concepts become Moodle concepts. Its output, the Moodle course model, is a release-aware JSON document: it already says which activity type, which question bank style and which file handling to use for the target Moodle release. Writers only execute it.

MoodleCloud administrator setup

  1. In Site administration, enable web services and the REST protocol.
  2. Create the external service "Cogniate integration" with the functions above, restricted to authorised users.
  3. Choose how packages arrive. Option A (recommended): a dedicated account cogniate.integration with a Manager role on the target category; packages reach the admin as a signed download link with a direct link to the Restore page. Option B (fewer clicks): the token is issued to the admin who performs restores, so packages are staged straight into their private files.
  4. Create the token with an IP restriction to the connector's published egress addresses and a valid-until date.
  5. Paste the site URL and token into the admin console. The connector confirms access with core_webservice_get_site_info.
  6. For live link, register the Cogniate tool under External tool, Manage tools, using the dynamic registration URL shown in the console.

8.3 Identifiers and idempotency

Course id number: cogniate:{courseId}:{variant}:{lang}. Short name: {courseCode}-{variant}-{lang}-v{major.minor}. Every activity carries cogniate:{itemId} in its id number, so the connector and plugin can find it again after restore or sync. Each item also stores a SHA-256 hash of its normalised content; an unchanged hash means no write. Every import job has an idempotency key of tenant, site, course, version, variant, language and channel, so a retried request never creates a duplicate course.

## Goal

A Canvas admin can install Cogniate with Canvas Dynamic Registration instead of pasting the developer key JSON. The registration creates the Canvas platform **inactive** with the connection's binding ref. The operator grant is still the ownership proof; its redemption adopts and activates the staged platform.

## Scope

In:
- Canvas profiles get `dynamicRegistration: { issuerRule: 'profile', registrationToken: 'opaque-bearer' }`.
- `issuerRule: 'profile'`: the configuration issuer must equal the profile issuer, and every endpoint must equal the filled profile value (auth and JWKS fixed; token `{serviceUrl}/login/oauth2/token`). Any other value refuses the registration; nothing is stored.
- The configuration URL is https, fetched with the guarded client; its host is the connection's site origin, its service origin, or a fixed host of the Canvas profile (`sso.canvaslms.com`).
- The registration request adds the Canvas extension members: privacy level `anonymous`, tool id `cogniate`, the vendor name; the scopes are `registration.scopes`.
- The platform is always staged: inactive, with the connection's binding ref.

Out: the optional `tokenEndpoints` trait field (only after a CANVAS-HOSTED row, LA-ADR-05 D6 "Dependency"); live rows (LA-H3).

## Design notes

- Option Y (BD-A2-95, ratified): a reserved issuer host keeps the M1 start page `ISSUER_RESERVED` (base contract §9.2; `lti/codes.test.ts` pins it); other reserved hosts, own hosts and failing host names get `PLATFORM_URL_NOT_IN_PROFILE`. Both refuse before any fetch.
- Option A (BD-A2-94, ratified): the floor refuses only host names that fail site rule 2, own hosts and reserved hosts; http and IP literals stay with the guarded client (no request for http or a private IP; a public-IP Moodle keeps Dynamic Registration). No baseline change, no LA-IC.
- Pre-fetch floor (BD-A2-93): the start route keeps the union rule (the loosest rule of any loaded profile, LA-ADR-02 D5), above one floor for every profile: not https, a site-rule 1–3 failure, or a reserved host (a fixed host of any loaded profile) is refused before any fetch. No loaded profile can complete such a configuration (any-https rules refuse reserved hosts; the Moodle configuration path is on the Moodle site; BD-A2-89 refuses fixed Canvas hosts at `complete`), so the fetch would only be an outbound request for an unauthenticated caller.
- Portal companion (BD-A2-90): LA-E3-16 (lane P) gives Canvas Dynamic Registration its portal path (method choice, registration URL, pre-filled staged binding form). It is in the same cut group as this task and LA-E3-15.
- Origin rule (BD-A2-89; LA-ADR-05 D6 "Configuration URL"): P1. The start page checks the Canvas site rules before the fetch; `complete` derives the site and service origins from the configuration, checks them with the same rules, stores them on the always-staged platform, and the grant's adoption rule proves them; no app or contract field. Change to L's proposal: a configuration URL on a fixed Canvas host (`sso.canvaslms.com`, beta, test) is refused at `complete` with the AP-05-30 page (nothing stored, nothing sent) until the CANVAS-HOSTED live row; the site origin is never taken from the shared issuer. One unit test for that refusal. AC-05's "site origin or service origin" reads as the derived origins under the Canvas site rules.

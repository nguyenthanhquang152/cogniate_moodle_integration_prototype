## Goal

Every channel, Moodle included, implements the `ConnectionSetup` port in its `app.ts`. The kernel picks the authority strategy (`self` or `operatorGrant`) from the stored `binding_authority`, routes launches by it, and runs the operator CLI by it. The app LMS check applies the guard levels. The folder `services/cogniate-app/src/providers/` goes away. No behaviour changes.

## Scope

- In: P2 `ConnectionSetup` for the three channels (the Moodle create rules, six-value parser and `badPlatformFields` move into `packages/channels/moodle/app.ts`); P3 strategies (bind, disconnect, suspend, release); P4 launch router; the app LMS check with guard levels (app API delta §5); the grant CLI by authority (`app:grant` refuses a `self` connection; `--purpose add_deployment` needs `deployments.multiple`); `kernel/ports.ts` as a types-only public file (QA may import its types).
- Out: grant bound values and `--accept-staged` (LA-E2-04); the kernel admin-value adapter (LA-E2-03); A2's `--operator` and evidence flags (LA-E5-12, lane K, B2, after this task).

## Design notes

- `kernel/ports.ts` holds every type of the D5 sketches (`ConnectionSetup`, `PortContext`, `ChannelSql`, `ExtensionRoute`, `PublishHook`, `PackageExporter`, …) so that LA-E1-08 adds no new public type file.
- The `ProviderAdapter` "pure" rule (`providers/types.ts:1-4`) moves to `app.ts`: no database, no LTI call.
- Requests from LA-E1-11 (RQ-1, BD-A1-24, BD-A1-25): add `bindingAuthority` (the stored `connection.binding_authority`) to the connection DTO in `app/connections.ts` (LA-IC-01; app API delta §1); add the optional manifest text `texts.registered` to the kernel manifest schema (default "Registered") and set it in the Moodle manifest ("Registered — activate in {LMS}").
- BD-A1-17: this task removes the transitional `providerOf(channel)` lookup with `providers/`; from now on the injected registry carries each channel's `app.ts` adapter, and the callers of the binding helpers take the adapter from it.
- Per-profile data (BD-A1-29): each `app.ts` exports the port field `profiles` (`{ sharing, serviceUrl, label, refusedHostSuffixes? }` per offered profile; type `AppProfileData` in `kernel/ports.ts`) instead of `profileLabel`, `acceptsServiceUrl` and `siteRuleSuffixes`; `sharingOf` reads it or goes. The AC-10 test also compares `serviceUrl` and `refusedHostSuffixes` with `lti-profiles.ts` and checks that every manifest registration profile has an entry.
- The per-profile `sharing` data of the adapters (BD-A1-12, from LA-E1-06) moves into each channel's `app.ts`. A unit test compares it with the `sharing` trait of the same profile in the channel's `lti-profiles.ts` (AC-10).

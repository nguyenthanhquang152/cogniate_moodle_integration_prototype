## Goal

The Canvas channel offers Dynamic Registration. Its manifest gets a `dynamic` method with authority `operatorGrant`, so a Canvas registration stages an inactive platform and the operator grant still proves ownership. The capability `registration.dynamic` and the legacy flag `dynamicRegistration` become true for Canvas (LA-IC-14).

## Scope

In: the Canvas `registration` list gets `{ method: 'dynamic', authority: 'operatorGrant', profiles: <the Canvas profiles>, defaultProfile: <as manual> }`. The registry load check 6 passes (Canvas is `exclusive`, the method is not `self`).

Out: the LTI service rules (LA-E3-09); the generic staged DR flow of the app (LA-E2-04).

## Design notes

- Portal companion (BD-A2-90): the "Known gap" above is closed by LA-E3-16 (lane P, same cut group). It uses these `dynamic` binding rows and the staged DTO pre-fill.
- LA-IC-14 ships with this task and LA-E3-09. QA makes its reviewed test-change list (plan LD-9): the K0 legacy projection golden of Canvas; `tests/acceptance/M1/canvas/11-canvas-platforms.test.ts:218`, `:241`, `:257`.
- Follow-up K commit after merge `2cc2aa5` (A1 BD-A1-103, BD-A1-104; recorded by A1 at the Lead's request in this A2 spec):
  - Canvas README Registration row: "| Registration | manual with a developer key, or Dynamic Registration (method `dynamic`, Should, LA-IC-14), which stages an inactive platform; both methods bind with authority `operatorGrant`: the operator grant proves ownership | app contract §4.4; ADR-011 §7; LA-ADR-05 D6 |".
  - `setup.bindingFields`: after the three `manual` rows, the three `dynamic` rows of a staged registration, the same as `lti-generic`: `{ key: 'clientId', label: 'Client ID', kind: 'id', required: true, method: 'dynamic' }`, `{ key: 'deploymentId', label: 'Deployment ID', kind: 'id', required: true, method: 'dynamic' }`, `{ key: 'grantCode', label: 'Approval code', kind: 'grantCode', required: true, method: 'dynamic' }`. The portal pre-fills both ids from the DTO of the pending staged connection (`platform.clientId`, `platform.deploymentIds[0]`; app API delta §3.4); a field spec has no pre-fill attribute. The `manual` rows do not change; `GET /app-api/lms-providers` does not carry `bindingFields`; so no Canvas byte changes and no LD-9 entry.
  - Known gap (not this task): the Canvas portal uses its own `CanvasWizard` (P), not the shell manifest wizard, so these rows do not change the Canvas portal. `CanvasCreate` sends only `method: "manual"`, and a pending connection always gets the developer key JSON step and an empty binding form. A Canvas Dynamic Registration from the portal needs a P companion task (A2's design, LA-ADR-05 D6: "D6 removes the JSON paste and the typed client id"); until then Canvas DR works through the API only (the K1-SIM ACs of LA-E3-09 and this task use the API).

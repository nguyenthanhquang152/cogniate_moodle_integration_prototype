## Goal

Store the `registration_client_uri` and the registration access token of a generic Dynamic Registration, so that the service can read and update the tool registration at the platform with the spec's management flow.

## Files

| May edit | Must not edit |
| --- | --- |
| `services/lti-service/src/lti/registration.ts`, `http/routes/registration.ts`, `store/registrations.ts`, `store/platforms.ts`; new LTI migration (management columns; number by the Lead) | `http/app.ts` (S; a new route mount goes by RQ-1); app code |

## Scope

- In: store both values (the token sealed by the key provider); a read of the registration at the platform; an update of the tool configuration at the platform.
- Out: any portal UI; a Moodle change (Moodle DR stays "new only").

- Design detail beyond D5 item 9 is open. Before the build, the Author proposes the operator route and its audit action to A2 through the Lead (one paragraph); the ACs below do not depend on the route name.

## Goal

A client can repeat a create call safely: `POST /api/lineitems`, `POST /api/platforms` and `POST /api/platforms/:id/deployments` accept an optional `Idempotency-Key`. The same key and body within 24 hours gives the stored answer and no second create. Without the header, nothing changes.

## Scope

- In: header parse (1–64 characters `[A-Za-z0-9_-]`); record per (tool account, key, method and route, SHA-256 of the body); stored status and body; `422 IDEMPOTENCY_KEY_REUSED`; `409 IDEMPOTENCY_IN_PROGRESS`; 24-hour validity.
- Out: the hourly `idempotency-cleanup` job (LA-E5-20). Until it ships, records older than 24 hours are ignored, not deleted.

## Design notes

- AGS preflight (BD-A2-71; Reviewer-A A-LA-E5-16-03): for `POST /api/lineitems`, call L's `preflightCreateLineItem(ctx)` (RQ-1; `platform/ags.ts`) after `agsContext` and before `claimIdempotency`; its refusals are never claimed. Unit tests: a credential with only `lineitem.readonly` gets `403 SERVICE_NOT_AVAILABLE` with a key that has a stored `201`; after the scope comes back, the same key replays.
- Refusal texts (BD-A2-58; contract delta §1.3): `409 IDEMPOTENCY_IN_PROGRESS` carries `details.retryAfter` (seconds until the 60 s claim ends, at least 1) and its fixed description; `422 IDEMPOTENCY_KEY_REUSED` names the route, path id, target and body. The hook never stores these answers, so BD-A2-57 does not apply to them.
- Fix round (BD-A2-56, BD-A2-57; Reviewer-A A-LA-E5-16-01, -02): the fingerprint adds the resolved target (Bearer: path parameters; ltik and service: `{ platformId, deploymentId, contextId, lineItemsUrl }`); the lookup moves after the read-only target checks of `platformOf` and `agsContext`; `429`, `5xx` and any answer with `Retry-After` are not stored (the claim is abandoned); the replay `Retry-After` branch goes. Unit tests: the same key and body from a second course gives `422`; a deactivated platform gets `403 PLATFORM_NOT_ACTIVE`, not a replay; a platform `429` is not replayed, and the next call reaches the platform.
- Contract decisions (BD-A2-51; LA-ADR-06 D9 "Build rules"): the key is unique per tool account; fingerprint = method + route template + decoded path parameters + SHA-256 of canonical JSON (sorted keys, no whitespace, absent body = `null`); another fingerprint gives `422`. Only `2xx`/`4xx` answers are stored; after a `5xx` the running record is deleted; a running record older than 60 s is replaced. Admin routes: a replay writes one event that mirrors the stored answer, with `details.idempotentReplay: true` and the key; the hook `409`/`422` write one `refused` event; the action is the route's contract §5 action. `POST /api/lineitems` writes no audit event. Unit tests: the same key on another platform id gives `422`; a reordered body replays; a `5xx` frees the key; a stale running record is replaced.
- A header that breaks the grammar gives `400 INVALID_REQUEST` naming the header (the design fixes the grammar, not the code; `INVALID_REQUEST` is the base code for a bad request field).
- The record is written before the route runs (state "running") and completed with the answer. A `5xx` answer is not stored, so a retry can run again.

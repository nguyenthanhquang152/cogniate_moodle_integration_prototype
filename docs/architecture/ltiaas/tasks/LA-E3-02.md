## Goal

When the state cookie is missing at launch and the state row has a storage target, the service checks the launch, stores a single-use storage check, and answers a page that reads the state back with `lti.get_data` and posts it. The new route `POST /lti/launch/{account}/storage-check` compares the value with the state hash and then completes the launch exactly like the cookie path. The task then sets the trait value of every Canvas profile, so Canvas launches in frames work without third-party cookies.

## Scope

In:
- Rules 5–8: cookie present (unchanged); cookie missing without target (unchanged `STATE_COOKIE_MISSING`); cookie missing with target (checks 1, 3, then 4–14 and the claim policy, then the `storage_check` row and the page, no ltik); the storage-check route.
- The storage-check page: CSP with `form-action 'self'`, `Referrer-Policy: same-origin`, `lti.get_data` for the same key at origin O (1.5 s), then a hidden form post (`check`, `value`; empty value on no answer).
- The route checks the account status first, as login and launch do (contract delta §1.5): a `suspended` account gives the `403` page `TOOL_ACCOUNT_SUSPENDED` (no state, no ltik), a `closed` one the `404` page `UNKNOWN_TOOL_ACCOUNT` (A-LAB-03; it calls the status gate of LA-E5-04).
- The route: `Origin` must be the origin of `PUBLIC_LTI_URL`, else `400 INVALID_STATE` (`storage_origin`) and the row stays unused; then unknown, used or expired (120 s) gives `INVALID_STATE` (`storage_check_unknown_used_or_expired`); the row is marked used in the same statement; SHA-256 compare in constant time; empty value gives `STATE_COOKIE_MISSING` with the storage help text; mismatch gives `INVALID_STATE` (`storage_mismatch`); success makes the ltik and answers `303` as the cookie path. `GET` on the path gives `405` with `Allow: POST`.
- Logs: `launch_check_failed {check: "storage", code, detail}`; `launch_accepted {binding: "cookie" | "storage"}`.
- Retention: `store/storage-checks.ts` exports a cleanup function that deletes `storage_check` rows older than 10 minutes; the LTI retention job of LA-E5-19 (S1) calls it.
- Rule 1a values: every Canvas profile (also `canvas-sim-cloud`) gets `{ targetFrame: 'from-login', origin: 'authOrigin' }`. `standard`, Blackboard and `brightspace` stay `null`.

Out: the login page (LA-E3-01); the `lti-generic` value (A1's LA-E2-01 or LA-E2-03, rule 1a); tenant ids in logs (LA-E5-18); the simulator frame (QA-E2E).

Needs from S1 (one line each, RQ-1): the redaction name `storageValue` in `packages/shared/src/logger.ts` (security delta §11); the call of this task's `storage_check` cleanup function in the LTI retention job (`services/lti-service/src/jobs/retention.ts`, LA-E5-19).

## Design notes

- Storage-check CSP (BD-A2-103; QA-E2E LA-E7-07 P3): `form-action 'self' <T>`, where `<T>` is the origin of the account's `launchUrl` (resource link) or `deepLinkingUrl` (Deep Linking) that this check redirects to, computed per request from the stored prepared launch; one origin, never a wildcard. The rest of the CSP, `frame-ancestors https:` and `Referrer-Policy: same-origin` do not change. No LD-9 change (the page is new in LA). Unit test: the header in three cases (resource link, Deep Linking, a second account with an operator-set `launchUrl` on another origin). QA-E2E reruns `U4.platform-storage.positive` live.
- Storage-check origin guard (BD-A2-104, ratified as built in `02f5d420`): `<T>` only for a plain https origin (lower-case letters, digits, dots, hyphens, an optional port); else `form-action 'self'` only. Keep the guard table test (`;`, `,`, `"`, `http:`, IPv6 literal, not a URL). No write-time refusal and no log line in LA.
- No cookie fallback on the storage check (BD-A2-44; LA-ADR-05 D1 rule 8): a launch with a matching cookie never reads platform storage, so a parallel login that overwrites a 16-slot key cannot break it. Regression tests: a valid cookie still succeeds after its slot was overwritten; a cookie-less launch with an overwritten slot gives `storage_mismatch` and no ltik.
- `GET` (any method except `POST`) on the storage-check path gives `405` with `Allow: POST` (contract delta §2.2; Author unit test).

- The state is used up at check 3 also on the storage path. A failed storage check therefore needs a new launch from the LMS.
- The help text of the empty-value case is the text of rule 8: "Your browser blocked the Cogniate sign-in in this frame. Open the activity in a new window, or allow cookies for this site."
- LA-IC-06 ships here. QA makes its reviewed test-change list at this task (plan LD-9). The list is expected to be empty: today's simulator sends no `lti_storage_target`.

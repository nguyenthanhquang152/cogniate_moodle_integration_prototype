## Goal

QA builds the K0 suite: one `describe.each` over every registered channel for the manifest schema, registry uniqueness, the legacy projection, profile data rules, adapter purity and the capability guard table. A minimal canary channel under `tests/ltiaas/canary/` is loaded as a second root on every `npm run check`, so each commit proves that a new channel needs no kernel edit (F4).

## Scope

- In: K0 cases of TEST-STRATEGY §2.7 (legacy projection, K-CAP, K-PROFILE, K-ADAPTER, manifest schema for every channel and the canary); one canary with a manifest, one LTI profile and an `app.ts` with fixed data; an admin-value canary variant without `app.ts` (used by LA-E2-03).
- Out: registry load-check failure cases and the check 14 table (Author unit tests).

## Design notes

- K0 imports only the entry points of tasks README §3. A K0 case whose entry point is not yet in the tree is written first and wired when that task lands.
- K-ADAPTER (BD-A1-20; Reviewer-A A-LA-E7-01-02, Reviewer-B B-LA-E7-01-02): use only the LA-ADR-01 D5 `ConnectionSetup` names and result shapes (D5 "Contract surface for K0"). A missing required member fails the case; no silent skip. A strict-body refusal is `{ ok: false, fields }`, not a throw. The canary `app.ts` implements D5 (pure, fixed data, the D1 file rules of BD-A1-16). After LA-E1-07, the kit uses `import type` from `kernel/ports.ts`.
- K-CAP (Reviewer-A A-LA-E7-01-01): the guard rows are those of LA-ADR-01 D3 (for example `registration.dynamic` → `422 CAPABILITY_NOT_SUPPORTED` with `details.capability` `dynamicRegistration`); the case calls product code, never compares the kit's table with itself.

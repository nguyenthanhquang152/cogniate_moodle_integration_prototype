## Goal

Dynamic Registration works for any kind A platform: an issuer with a path, an opaque registration token, endpoints that follow the profile rule, the `authorization_server` audience, capability checks with clear pages, the profile from the app at `complete`, and stored granted scopes. When the configuration breaks I-SELF, `complete` stages an inactive platform with the connection's binding ref instead of a `self` binding. Moodle at the host root behaves as before.

## Design notes

- Token kinds (A1 BD-A1-76, BD-A1-77): the trait value is `scope-jwt` (renamed from the LMS-named value; F1 stays 0). The start page stores the kind it found in `registration_session.token_kind` (new LTI migration `021`: `TEXT NULL CHECK (token_kind IN ('scope-jwt', 'opaque-bearer'))`); `complete` checks the chosen profile's `registrationToken` against the stored kind and refuses a mismatch before any registration request; `NULL` = an old row = `scope-jwt` (today's behaviour). No second JWKS fetch at `complete`, so the T3b and G4 goldens stay.
- Pending-tool text (A1 BD-A1-87; Codex Reviewer-B question): `toolMayExist` at `complete` takes the channel's `texts.registration.TOOL_MAY_EXIST` (`{LMS}`, `{tool}` filled), else the core default "{LMS} may have saved the Cogniate tool already. If {LMS} shows the tool '{tool}', delete it there, then connect again."; the Moodle manifest holds today's sentence, so G4 does not change; the answer stays `PLATFORM_ERROR` / `tool_may_exist`. The kernel key and the Moodle value: K by RQ-1, or one RQ-2 commit in this round.
- Local choices ratified (A1 BD-A1-84): the start rule from the loaded DR profiles; a JWKS fetch failure stays `FETCH_FAILED` even when an opaque token is allowed; `bindingRef` required at `complete` for every `any-https` profile, stored only when staged; a staged registration that meets an existing platform sets it inactive. The same commit as the flag removal sets `dynamicRegistration: null` explicitly in the Canvas and Blackboard profile files (BD-A1-83).
- Legacy flag removal (A1 BD-A1-75): after the lead QA has landed its change (`tests/ltiaas/k0/contract.test.ts` asserts `clientAssertionAud.form` instead of `clientAssertionAudArray`; the two canaries drop the flag), one commit removes `clientAssertionAudArray` from the kernel `ProfileSource` type (one line, RQ-2), the LTI schema (`profiles/**`) and the three baseline `lti-profiles.ts` (flag lines only).
- Keys (A1 BD-A1-68): `texts.registration.ISSUER_MISMATCH` holds the registration help line that the DR page shows (help replaces the action); the `lti/codes.ts` `ISSUER_MISMATCH` action becomes "The platform configuration is not from the site that started the registration. Start the registration again from {LMS}." after this task confirms that no page or answer shows it (if one does, that place uses the same key). New key `INVALID_OPENID_CONFIGURATION` for its help line ("…Start the registration again from Manage tools. …" in the Moodle manifest, byte for byte); core default "{LMS} sent a registration that Cogniate cannot use. Start the registration again from {LMS}. If it happens again, give the trace id to your Cogniate contact." The kernel key and the Moodle value: K by RQ-1, or one RQ-2 commit inside this task.
- DR help sentences (A1 BD-A1-59; Reviewer-B B-LA-E1-10-01): `REGISTRATION_HELP` (`UNKNOWN_TOOL_ACCOUNT`, `INVALID_REQUEST`), `ISSUER_MISMATCH` (`lti/codes.ts`) and `REGISTRATION_UPDATE_NOT_ALLOWED` take their sentence from the channel manifest `texts.registration` with `{LMS}` filled; a channel without a sentence gets a core default with no menu path (for example "Start the registration again from {LMS}."); with no known channel, the no-context channel's sentences apply (today Moodle). The Moodle manifest holds today's sentences byte for byte (kernel schema field and Moodle values: K by RQ-1, or one RQ-2 commit). `FETCH_FAILED` has no menu path and stays a core text.
- Family guard phases (A1 BD-A1-54, BD-A1-55): the DR family check (`http/routes/registration.ts`, on the configuration's `product_family_code`) calls `familyGuardVerdict(…, 'registration')`; it is the only registration-phase call site. Check 14 calls it with `'launch'`. The refusal page and log output stay byte for byte.
- Family guard (A1 BD-A1-43): this task switches the DR family check (AC-05) and the launch check 14 to the kernel function `familyGuardVerdict(registry, family, profileChannel, level)` (BD-A1-39, from LA-E1-07). It may edit `services/lti-service/src/lti/checks.ts` for the check 14 call switch only; the LA-E1-05 tests must still pass.
- Q-LAD-24: a learner launch on a staged, inactive DR platform gets `PLATFORM_NOT_ACTIVE` (the LTI service refuses the login). `deployment_not_approved` is the app oracle of A2 AP-08-04, where the staged record is active; it is not used here.

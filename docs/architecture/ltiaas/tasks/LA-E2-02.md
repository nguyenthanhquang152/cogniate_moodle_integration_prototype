## Goal

Dynamic Registration works for any kind A platform: an issuer with a path, an opaque registration token, endpoints that follow the profile rule, the `authorization_server` audience, capability checks with clear pages, the profile from the app at `complete`, and stored granted scopes. When the configuration breaks I-SELF, `complete` stages an inactive platform with the connection's binding ref instead of a `self` binding. Moodle at the host root behaves as before.

## Scope

- In: D5 items 1–8 and 10; the start page applies the loosest rule; `complete` applies the exact rule of the chosen profile before it sends anything; DR page texts with `{LMS}` of the connection's channel.
- Out: item 9, DR management (LA-E2-07, Could); the app side of the staged registration (LA-E2-04); Canvas DR (A2 LA-E3-09).

## Design notes

- Family guard phases (A1 BD-A1-54): the DR family check calls `familyGuardVerdict(…, 'registration')`, check 14 calls it with `'launch'`; the refusal and log output stay byte for byte.
- Family guard (A1 BD-A1-43): this task switches the DR family check (AC-05) and the launch check 14 to the kernel function `familyGuardVerdict(registry, family, profileChannel, level)` (BD-A1-39, from LA-E1-07). It may edit `services/lti-service/src/lti/checks.ts` for the check 14 call switch only; the LA-E1-05 tests must still pass.
- Q-LAD-24: a learner launch on a staged, inactive DR platform gets `PLATFORM_NOT_ACTIVE` (the LTI service refuses the login). `deployment_not_approved` is the app oracle of A2 AP-08-04, where the staged record is active; it is not used here.

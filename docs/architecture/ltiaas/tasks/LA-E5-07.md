## Goal

A tool account can have up to two active API keys, each with scopes (`launch`, `admin`), an optional expiry, a last-use time and a revoke. This gives key rotation with overlap, and a leaked launch-side key can no longer change platforms. The existing `cogniate` key keeps working unchanged.

## Scope

In:
- Table `api_key` of LA-ADR-06 D5; migration backfill: one row per account from `tool_account.api_key_hash`, label `bootstrap`, scopes `["launch","admin"]`, no expiry. The old column stays and is no longer read. Backfill values (id, `prefix` `NULL`, `created_at`, `created_by`): LA-ADR-06 D5 "Backfill values" (BD-A2-09).
- The bridge in `store/accounts.ts` until LA-E5-05 (`ensureAccount`, rotation, `findAccountByApiKey`): LA-ADR-06 D5 "Bridge until LA-E5-05" (BD-A2-10). Who edits `accounts.ts` is the Lead's process call. S2 gives the synchronous store API that the bridge calls (issue, revoke all active keys of an account, lookup).
- Lookup by SHA-256 hash; format `ltis_` + 43 base64url characters (unchanged).
- Scopes: `launch` = LTIK-AUTH-V2 and SERVICE-AUTH-V1 routes; `admin` = every Bearer route; missing scope gives `403 API_KEY_SCOPE_MISSING` (contract delta §1.2).
- At most 2 active keys: a third issue gives `409 API_KEY_LIMIT`.
- Emergency rotation (BD-A2-33): the issue body takes the optional `revokeOthers: true`. In one transaction it revokes every active key of the account, then issues; the limit counts after the revoke. One `api_key.issue` event with `details.revokedKeyIds`. Author unit test: with two active keys, the call gives `201`, both old keys give `401`, and the new key passes.
- Expiry 1 hour to 2 years from now; outside the range `400 INVALID_REQUEST` (field `expiresAt`); an expired or revoked key gives the same `401` code as an unknown key.
- `last_used_at` updated at most once per minute per key.
- Endpoints `GET`, `POST /operator/v1/accounts/:id/api-keys`, `POST …/api-keys/:keyId/revoke`, with audit events `api_key.issue`, `api_key.revoke`.
- Close of an account (LA-E5-04) revokes every `api_key` row of the account.
- Closed account (BD-A2-12): issue gives `409 ACCOUNT_CLOSED`; `GET …/api-keys` and revoke stay available (revoke is idempotent). A `suspended` account can get keys. The status check is the one accounts-store helper of S1 (LA-ADR-06 D2 "Operator writes on a closed account"), called inside the `audit.change` transaction.

Out:
- `lti:bootstrap --rotate-api-key` as an API client (LA-E5-05).
- `api-key-expiry` job (LA-E5-20). Tenant route `GET /api/account` (Should, LA-E5-15).

## Design notes

- The `auth_failure` rule of LA-E5-03 reads "unknown, expired or revoked" from this lookup; keep one function that answers both.
- Behaviour change only for keys without a needed scope; no existing key lacks a scope (LA-IC-10, row "API key table").

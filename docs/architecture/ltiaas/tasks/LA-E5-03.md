## Goal

The LTI service limits requests per rate-limit class with token buckets. No bucket may let one sender block every tenant: the account classes are soft, and only API key or operator key failures spend `auth_failure`. Operators change the limits at run time through the operator API.

## Scope

In:
- Token bucket per (class, key) in a bounded in-memory map (at most 100,000 keys, least recently used first out).
- The classes and defaults of LA-ADR-06 D1, with the mode column: `protocol`, `registration`, `keys`, `api`, `admin`, `auth_failure`, `operator` hard; `protocol_account`, `registration_account` soft.
- Order: address classes in an `onRequest` hook, by path, before any database read; `api` and `admin` after the whole authentication passes; `operator` after the operator key lookup.
- `auth_failure`: spent only when the API key or operator key fails (no or malformed header, unknown, expired or revoked key). An ltik or service key `401` under a valid API key spends no bucket (A-LAD-02).
- Client address: socket address; IPv6 keyed by its /64; `X-Forwarded-For` only from `TRUSTED_PROXY_CIDRS` (CIDRs or host names, names resolved at start and every 60 s); compose value `proxy` in every profile.
- Answers: `429 RATE_LIMITED` with `Retry-After` on API routes; the `429` HTML page `RATE_LIMITED` on protocol routes. Page codes `RATE_LIMITED`, `TOOL_ACCOUNT_SUSPENDED`, `REGISTRATION_SESSION_LIMIT` and their action lines in `lti/codes.ts` (contract delta §1.3).
- Logs `rate_limited` and `rate_limit_soft` (at most once per bucket per minute); metric hooks are LA-E5-17.
- Settings precedence: per-account `limits` (column from LA-E5-04), then `service_setting` key `rate_limits`, then `LTI_RATE_LIMITS`, then the built-in table. `registrationSessionsPerAddress` is in the same setting.
- `GET`, `PATCH /operator/v1/rate-limits` (contract delta §3); one `settings.rate_limits` audit event per change; a change applies at once.
- An exported session-cap function: open sessions per (client address, tool account) against `registrationSessionsPerAddress` (default 10).

Out:
- The call of the session cap at registration start and the status pages (LA-E5-06).
- Metrics and alerts (LA-E5-17; operability §5).
- App-edge limit on `/tool/launch`, `/tool/deep-link` (A1, app API delta §5a).

## Design notes

- `/healthz`, `/readyz` and `/metrics` are never limited.
- Per-account overrides read the `limits` column that LA-E5-04 adds; AC-LA-E5-03-01 runs after LA-E5-04.
- Shared state (Q-LAB-04): every AC that changes a limit restores it in its clean-up (`PATCH /operator/v1/rate-limits {classes: {<class>: null}}`, tasks README §2 AL-4); per-account values use a fresh account, never `qa-second`.
- Author unit tests (no AC here): the bucket map bound with least-recently-used eviction; the exported session-cap function per (client address, tool account). LA-E5-06 proves the cap end to end.
- Behaviour change: `429` above the limits (LA-IC-10, row "Rate limits"). QA records the peak rate per class, the peak `auth_failure` rate and the peak open sessions per address at E0; if a suite goes above a default, the `acceptance` compose raises it with `LTI_RATE_LIMITS`. No assertion changes.

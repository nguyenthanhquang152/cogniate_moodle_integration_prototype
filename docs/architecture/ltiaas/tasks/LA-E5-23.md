## Goal

The LTI service reaches its data only through async store interfaces (`LtiStore`) with the SQLite adapter behind them. Then LG can add a Postgres adapter without a rewrite. The engine does not change in LA (LD-3, LA-H5).

## Scope

- In: async interfaces per store area; the SQLite adapter; the portability lint of D13 item 2 for all LA SQL (no `rowid`, no `X''` literals, no SQLite date functions; the audit trigger is listed as SQLite adapter code); one comment block in the store index that lists the in-memory state that LG must move (D13 item 4: score clock, platform token cache, platform JWKS cache, rate-limit buckets).
- Out: a Postgres adapter, row-level security, the data move (LG); the app records (A1, with E4).

## Design notes

- Port shape (BD-A2-96; LA-ADR-06 D13 item 3 "Build rules"): async per-area `LtiStore` methods over private synchronous SQL. Each compound or audited write is one atomic store method (change, `ok` event, `afterCommit` callbacks in one synchronous transaction); routes await one method; there is never an `await` inside `transaction()` or `audit.change` (D4 T2). Structural call-site changes are in scope. Production SQL moves verbatim into `store/**`. The audit-retention `DELETE` gets its own store module (not `store/audit.ts`, which stays insert and list only), and lane P moves the F5 `audit-event-delete` allowed path (`infra/scripts/fitness/rules/audit-event-delete.mjs` `ALLOWED`) to it in the same merge.
- Keep every SQL statement as it is; only the function signatures become async. This keeps behaviour equal and the review small.

## Goal

A developer or agent who is new to the repo adds a kind A LTI LMS by following one guide: one channel folder, one simulator module, one host manifest entry, one kit fixture. The guide states only behaviour that QA verified, and it names the checks that prove the result (F2, K0, K1, K2 U3).

## Files

| May edit | Must not edit |
| --- | --- |
| New `docs/guides/ltiaas/add-a-channel.md` | Product code; `docs/architecture/**`; other guides |

## Scope

- In: the folder layout and the import rules; the manifest fields with the `lti-generic` and `brightspace` examples; admin-value profiles and `FieldSpec.default`; guard levels and when a family may be guarded; the simulator module and the host manifest entry; the kit fixture; the F2 command and the expected report; a step that finds live Moodle `standard` connections of the LMS before a new named channel guards its family.
- Out: kind B platforms (they need an ADR revision for `launch`-level guards); a new capability (a kernel change with an ADR revision).

## Design notes

- The Moodle step (Reviewer-B round-3 note 2, A-LAD-19): before the new channel guards family F at the `registration` level, the operator lists the platforms with `productFamilyCode` = F on the `standard` profile (operator API, A2) and moves each such connection to `lti-generic` first; after the new channel ships, a launch of F on a `standard` platform is refused (LA-ADR-02 D1).

## Goal

The OIDC login can store the state in the platform's client-side storage. When the platform profile has `platformStorage` and a storage target exists, the login answers a `200` page that sends `lti.put_data` and then goes to the auth URL. In every other case the login answers today's `302`, byte for byte. This task builds the login side and the state columns; LA-E3-02 builds the launch side and switches the Canvas profiles on.

## Scope

In:
- Rule 1: the trigger. The trait is not `null` and a target exists: `from-login` reads `lti_storage_target` (query or form body); a frame name in the trait is the target itself.
- Rule 2: the storage origin O (`authOrigin` = the origin of the platform `authenticationEndpoint`; else the fixed origin of the trait); the target window (`_parent` or `window.parent.frames[T]`); a top-level page skips the storage step.
- Rule 3: the login page (headers, CSP, the escaped JSON block, the key `cog_state_<d>`, the 1.5 s wait, the same auth URL as the `302`).
- Rule 4: the two state columns.
- Rule 9 for `lti.put_data` replies (origin O, `.response` subject, same `message_id`; an `error` reply counts as no answer; never post to `*`).

Out: the launch side, the storage-check page and route, the `storage_check` table and the trait values (LA-E3-02); tenant ids in the log lines (LA-E5-18); the simulator forwarding frame (QA-E2E, TEST-STRATEGY §2.8).

## Design notes

- Static login page text (BD-A2-41): visible "Opening the activity. Please wait."; `<noscript>`: "This activity needs JavaScript. Turn on JavaScript in your browser, then open the activity again from your course." No request data in the text; the CSP does not change.
- One function builds the auth URL for both answers. The `302` `Location` and the page's auth URL come from it, so they cannot differ.
- An invalid `lti_storage_target` (more than 64 characters, or characters outside `[A-Za-z0-9_-]` and not `_parent`) counts as "no target": the login answers the `302`.
- The page carries no request value in HTML or script text, except inside the JSON block. The script reads the block with `JSON.parse`. A new nonce per answer.
- `<d>` is the first hex digit of SHA-256 of the state (16 keys at most per tool origin).
- No profile has a non-`null` trait in this task, so the product shows no change. The unit tests use a test profile with the trait set.
- First commit, behaviour-neutral (A1 BD-A1-33): the trait `platformStorage: null | { targetFrame: 'from-login' | <frame name>, origin: 'authOrigin' | <fixed https origin> }` in the kernel `ProfileSource` type and the LTI schema; optional in a profile file (absent = `null`, normalized by the registry); a frame name is `_parent` or `[A-Za-z0-9_-]{1,64}`; a fixed origin is a canonical `https` origin with no path. The baseline `lti-profiles.ts` files do not change.
- The login handler in `http/routes/protocol.ts` writes the page result (status `200`, the page headers, the state cookie, the HTML) when `initiateLogin` gives the page, and today's `302` otherwise (A1 BD-A1-34). AC-03 tests it at the route.

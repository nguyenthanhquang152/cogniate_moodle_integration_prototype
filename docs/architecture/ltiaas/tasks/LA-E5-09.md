## Goal

Operators can see which key versions are in use and move every sealed blob to the active version. After a complete re-wrap, the service refuses legacy blobs, so associated data protects every sealed row. This completes the master-key rotation procedure of operability §6.3.

## Scope

In:
- `GET /operator/v1/key-provider` → `{ kind, activeVersion, versions: [{ id, state, sealedCount, derivedCount }] }` (contract delta §3).
- `POST /operator/v1/key-provider/rewrap` → `202 { job: "key-rewrap", traceId }`; it starts the on-demand job through the runner (`runNow`).
- Job `key-rewrap`: batches of 100 rows per transaction; re-seals every blob whose version is not active (also legacy blobs); idempotent and resumable; one `job_run` line per run.
- Audit: one `key_provider.rewrap` event for the request, and one more at the job end with counts (contract delta §5).
- Legacy refusal (A-LAD-16): a run that ends with no legacy blob in any sealed column stores `legacyBlobs: refused` in `service_setting` (key `key_provider`) and writes one audit event; from then on `open` refuses a blob without the header and logs `key_open_failed {table, reason: "legacy_refused"}`.

Out:
- The provider, the blob format and `ready()` (LA-E5-08). `/readyz` (LA-E5-17).
- App sealed columns (LA-E5-22).

## Design notes

- Authenticated metadata (BD-A2-38): `LocalKeyProvider.openWithMetadataSync(blob, aad)` returns `{ plaintext, version, legacyFormat }` from the decryption path whose tag passed, in its own commit. Re-wrap re-seals when `legacyFormat` or `version !== active`. `legacyBlobs: refused` is stored only when a complete run opened every sealed blob with `legacyFormat: false`. No `hasBlobHeader` export. Author unit test: a legacy blob whose IV parses as a valid `cgk1` header is re-sealed, and the refusal is not stored in that run.
- Bounded run (BD-A2-36; LA-ADR-06 D6 "Re-wrap"): one synchronous transaction per batch of at most 100 rows, with a compare-and-set update; the lease (at least 10 s left) and `ctx.signal` are checked at the start of each batch; it yields between batches; a stopped run ends as `partial`, and the next operator call continues. Exactly two audit events: the request event and the job-end event (`outcome`, counts, `legacyBlobsRefused` when the setting is stored in the same transaction). A failed run has `result: failed` with the error class (the type value `failed` is added to S1's `store/audit.ts` by RQ-1). Author unit tests: the lease deadline stops before a batch; the abort signal stops; a changed row is skipped; complete with no legacy blob left stores the setting and one end event; a thrown error gives a `failed` end event and keeps the earlier batches.
- `sealedCount` counts blobs; `derivedCount` counts `service_key` rows by derivation version. The re-wrap changes only `sealedCount`. `legacy` stays in the ring while `derivedCount` of `legacy` is above 0 (operability §6.3 CAUTION).
- Audited changes and re-wrap batches run in a synchronous `transaction()` (LA-ADR-06 D4 rule T2). `KeyProvider.seal` is async: inside a transaction use `sealSync` and `openSync` of the local provider, or seal before the transaction. Never pass an `async` callback to `transaction()` or `audit.change`.
- The procedure for QA (AC-LA-E5-09-02): QA writes `infra/.secrets/lti/keyring.json` in its own clone and restarts the LTI service (tasks README §2 allowance, README OC-7).

## Goal

The simulator loads its providers from data, and one host manifest gives the compose aliases, the certificate SANs and the `acceptance` allowlist. After this task a new simulator LMS is one module plus one manifest entry, with no infra edit. Two new providers serve E2: a generic provider and a D2L provider.

## Scope

- In: data-driven provider loading; the host manifest `tests/sim/hosts.json` that LA-E7-03 reads; the generic provider (issuer with a path, token on a second host, many deployments, and a Moodle-shaped config with issuer = site origin); the D2L provider (token host `auth.brightspace.sim.test`, an audience different from the token URL, family `desire2learn`, UUID deployments).
- Out: scenario options for E3, E4 and E6, and the platform side of Dynamic Registration (LA-E7-05).

## Design notes

- Every new behaviour is a scenario option with today's default, so M1, M2 and the simulator self-tests see no change (TEST-STRATEGY §2.5).
- `tests/sim/hosts.json` has the format and the fail-closed rules of [README §4b](../README.md#4b-simulator-host-manifest-f74) (BD-A1-01): `{"version":1,"providers":[{"id","aliases","allowlist"}]}`, one entry per provider id, hosts end in `.sim.test`, `allowlist` ⊆ `aliases`, `lms-sim.test` never in the file; the simulator refuses a start when its loaded provider ids and the entry ids differ, or when one host is in two providers.

## 1. Who verifies what

Independence rule: each QA session is separate from the authors it verifies and from the reviewers. It writes its tests from the approved criteria before it reads author code or notes, and it stays blind to other new reports until it submits. Since the owner's 2026-10-20 direction, all remaining roles use Claude Code Opus 5.5 xhigh, so new QA reports are independent but are **not** cross-model reviews. Earlier cross-model results stay valid with their original model attribution. The existing evidence gates do not change.

## 2. Evidence labels

Every evidence row has one label: `SIM`, `MOODLE-LIVE`, `CANVAS-HOSTED`, `CANVAS-LOCAL`, `BLACKBOARD-LIVE` or `DOC` (ADR-011 §13). Every result records the AC and subcase, product SHA, test SHA, command, run id, image digests, profile, health output, time and redacted artifact path. A live row also records the environment, profile, LMS version, browser (name, version, operating system, cookie setting) and date. A `SIM` PASS says: "our service behaves as the documented provider behaviour in a signed simulation". It never says "works with Canvas" or "works with Blackboard". A `CANVAS-LOCAL` PASS never fills a `CANVAS-HOSTED` row. A skipped test or an empty selection never satisfies an AC.

### 3.2 Simulator behaviour (QA builds it)

Keys: a new RSA 2048 key pair per start (no private key on disk, none in git), published at the JWKS paths below. Time comes from the system clock. Simulator self-tests reject tampered tokens. Pin the provider-source revision used for fixtures in the evidence.

| Host | Paths | Behaviour |
| --- | --- | --- |
| `sso.canvas.sim.test` | `GET /api/lti/security/jwks`; `GET` and `POST /api/lti/authorize_redirect` | Checks `client_id` (a known simulated key), `redirect_uri` = `{PUBLIC_LTI_URL}/lti/launch/cogniate` exactly, `response_type=id_token`, `scope=openid`, `state`, `nonce`, and that `login_hint` and `lti_message_hint` are the values it sent. Then it answers an auto-submit form that POSTs `id_token` and `state` to `redirect_uri`. Canvas scenarios use `document_target: "iframe"` (F-CV-17) and `tool_platform.product_family_code: "canvas"` (F-CV-22) unless a test sets otherwise on purpose. Canvas Deep Linking requests put `data` only in the query of `deep_link_return_url` and have no `deep_linking_settings.data` claim (F-CV-21). |
| `school-a.canvas.sim.test`, `school-b.canvas.sim.test` | `POST /login/oauth2/token`; AGS `/api/lti/courses/{c}/line_items` (`GET`, `POST`), `…/line_items/{id}` (`GET`, `PUT`, `DELETE`), `…/scores` (`POST`), `…/results` (`GET`); NRPS `/api/lti/courses/{c}/names_and_roles`; DL return `POST /courses/{c}/deep_linking_response`; a frame page `GET /__frame?url=` | Token: verifies the client assertion with `{PUBLIC_LTI_URL}/lti/keys/cogniate` (signature, `iss = sub` = client id, `aud` = this URL, dates, unique `jti`, grant type, scopes) and records the `aud` form. | `canvas.school-a.sim.test` | DL return; frame page | A Canvas page host that differs from the service host (F-CV-18, AC-M1-32). No token, AGS or NRPS here. |
| `canvas-self.sim.test` | auth, JWKS, and the Canvas page paths | Self-hosted Canvas: issuer `https://canvas-self.sim.test`; product family `canvas`. |
| `api.canvas-self.sim.test` | token, AGS, NRPS | The separate service origin of the self-hosted Canvas (AC-M1-26). |
| `developer.blackboard.sim.test` | `GET /api/v1/management/applications/{clientId}/jwks.json`; `GET /api/v1/gateway/oidcauth`; `POST /api/v1/gateway/oauth2/jwttoken` | As the Canvas auth and token endpoints. | `learn-a.blackboard.sim.test`, `learn-b.blackboard.sim.test` | AGS `/learn/api/v1/lti/courses/{c}/lineItems…`; NRPS `/learn/api/v1/lti/external/namesandroles/{c}`; DL return `POST /webapps/blackboard/controller/lti/v2/deeplinking` | As Canvas sites. Production profile values are checked only as constants (AC-M1-01, AC-M1-02 and the Author's unit tests). No test calls a real vendor host.

### 3.3 App-to-LTI transport gate (acceptance only)

The LMS simulator cannot pause the app's internal calls to the LTI service. For the redemption, disconnect and recovery races (AC-M1-37, AC-M1-38), the `acceptance` profile adds a gate between them. The Author builds the service (`infra/**`); QA owns its scenarios and assertions.

| Item | Value |
| --- | --- |
| Service | `lti-gate`, `acceptance` profile only; plain Node, no npm install; host name `lti-gate.test` (QA leaf SAN; app allowlist in `acceptance` only) |
| Routing | In `acceptance`, the app sends its LTI service API calls (`/api/*`) to `https://lti-gate.test`, which forwards them to the real LTI service. Browser protocol traffic does not pass the gate. In every other profile the app calls the LTI service directly, as today. |
| Control | `POST https://lti-gate.test/__gate/rules` (a list of rules: `id`, `method`, `pathRegex`, `action`, `times`; it replaces the rule list; held requests stay held), `POST /__gate/release {requestId, then: "deliver" or "drop"}`, `GET /__gate/events?since=<event seq>&requestId=<id>`, `POST /__gate/reset`. `/__gate/*` is never forwarded. |
| Rule match | Rules are checked in list order. The first rule whose `method` and `pathRegex` (on the path without query) match, and whose `times` is above 0, applies; its `times` decreases by 1. A request that matches no rule passes. So QA can hold the first `PATCH` of a path and fail the second one with two rules. |
| Actions | `pass`; `fail_before` (answer `503` without forwarding); `hold_before` (forward only after release); `hold_after` (forward, keep the answer until release, then deliver it or close the caller's connection); `drop_after` (forward, then close the caller's connection without an answer). |
| Request id | The gate gives each request that a rule matched a new id (`g-<n>`, increasing). Release, events and the log use it. |
| Phases (events) | `received`, `failed_before`, `held_before`, `forwarded`, `upstream_completed` (with the upstream `status`), `held_after`, `delivered`, `dropped` (the gate closed the caller without an answer), `caller_gone` (the caller closed first, for example at its 5 s timeout). Each event has `seq`, `ts`, `request_id`, `rule_id`, `method`, `path` (no query), `phase`, `status` (if any). No header, body, query or secret. |
| Caller gone | The gate never aborts an upstream call because the caller left. A `hold_before` request whose caller is gone stays held; `release … deliver` still forwards it (`forwarded`, `upstream_completed`), and the gate discards the answer. This is the **late write** of app contract §4.7.1. `release … drop` never forwards it. A `hold_after` answer whose caller is gone is discarded on release. |
| Limits | A held request is held at most 600 s; then the gate drops it without forwarding (`dropped`, with `reason: "hold_limit"`). `POST /__gate/reset` drops every held request without forwarding, clears the rules and keeps the event log. QA calls reset at the end of each subcase; QA owns this cleanup. |
| Timeouts | The gate delays network traffic only. It does not pause an app handler or change its 5 s timeout, and no production timeout changes. A schedule that needs a live handler must release within that 5 s; a schedule that needs a late write waits for `caller_gone` first. QA polls `GET /__gate/events` (and public state) with deadlines; a fixed sleep is not proof that a phase happened. |
| Log | `/logs/lti-gate.jsonl`: the same event objects (`{event: "gate_event", …}`). |
| Scope | It changes no URL check of either service and adds no production code path. |

## 6. QA run order

1. QA builds the simulator, the gate scenarios and the M1 tests from this spec, before reading any M1 code.
2. QA runs the LTI-only subcases on the M1a SHA (partial evidence only; Q-M0-07), then all M1 criteria on the M1 SHA, including the populated `011→012` route in both full runs. An AC passes only on the full M1 run.
3. QA-E2E runs M2 criteria on the merged M1+M2 SHA.
4. QA-E2E (T7) and QA (legacy suites) run the Moodle regression (AC-M3-02) on the final SHA; QA runs AC-M1-23 and AC-M1-30 in their own clone.
5. QA-E2E records the live matrix.

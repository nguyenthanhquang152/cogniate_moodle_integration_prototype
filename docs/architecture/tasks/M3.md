Owners: QA (Codex GPT-6-Astra, xhigh) and QA-E2E (Claude Code Opus 5.5, xhigh). Depends on: the M0 design gate (QA starts the simulator and tests from this spec at once); M1 and M2 SHAs for the runs. Test lanes (project prefix, port, subnet): [phase plan](../../team/multi-lms-plan.md), "Test environment decisions".

## 2. Evidence labels

Every evidence row has one label: `SIM`, `MOODLE-LIVE`, `CANVAS-HOSTED`, `CANVAS-LOCAL`, `BLACKBOARD-LIVE` or `DOC` (ADR-011 §13). A live row also records the environment, profile, LMS version, browser (name, version, operating system, cookie setting) and date. A `SIM` PASS says: "our service behaves as the documented provider behaviour in a signed simulation". It never says "works with Canvas" or "works with Blackboard". A `CANVAS-LOCAL` PASS never fills a `CANVAS-HOSTED` row.

## 3. Signed platform simulator

QA writes it in `tests/sim/`. The Author adds the compose service in M1 (`infra/**`). This section is the interface between them.

### 3.1 Compose service (M1 builds it)

| Item | Value |
| --- | --- |
| Service | `lms-sim`, `acceptance` profile only |
| Image | the same Node image as the existing QA helper hosts; no npm install (plain Node built-ins, like `infra/qa-hosts/qa-hosts.mjs`) |
| Command | `node /sim/server.mjs` |
| Mount | `tests/sim` → `/sim` (read-only); logs → `/logs` |
| Env | `LOG_DIR=/logs`, `CERT_FILE`, `KEY_FILE` (the QA leaf), `CA_FILE` (dev CA), `PUBLIC_LTI_URL` |
| Ports | 443 HTTPS (all sim hosts); 8080 plain HTTP `GET /healthz` only (not logged) |
| Network aliases | `lms-sim.test`, `developer.blackboard.sim.test`, `learn-a.blackboard.sim.test`, `learn-b.blackboard.sim.test`, `sso.canvas.sim.test`, `school-a.canvas.sim.test`, `school-b.canvas.sim.test`, `canvas.school-a.sim.test`, `canvas-self.sim.test` |
| Certificate | the QA leaf (`infra/.certs/qa.crt`) gets these names as SANs (the dev CA allows `*.test` names) |
| Allowlist | the LTI service `OUTBOUND_PRIVATE_HOST_ALLOWLIST` gets the hosts that the LTI service calls: `developer.blackboard.sim.test`, `learn-a.blackboard.sim.test`, `learn-b.blackboard.sim.test`, `sso.canvas.sim.test`, `school-a.canvas.sim.test`, `school-b.canvas.sim.test`, `canvas-self.sim.test`. Not `lms-sim.test` and not `canvas.school-a.sim.test` (a page host: only browsers use it). |
| Stack names | resolves the four stack host names (`PUBLIC_*_URL`) like the `e2e` container, so it can fetch `{PUBLIC_LTI_URL}/lti/keys/cogniate` and post to the launch URL |
| Log | `/logs/lms-sim.jsonl`, one line per request: `{ts, level, service: "lms-sim", event: "sim_hit", trace_id, host, method, path, status}` (no query, no token) |

`blackboard.sim.test` and `canvas.sim.test` are issuer values only. Nothing resolves or fetches them. No simulation uses a real vendor host name or certificate.

### 3.2 Behaviour (QA builds it)

The simulator acts as the documented provider (research facts, including the Canvas code facts F-CV-17 to F-CV-20). Keys: a new RSA 2048 key pair per start (no private key on disk, none in git), published at the JWKS paths below. Time comes from the system clock.

| Host | Paths | Behaviour |
| --- | --- | --- |
| `sso.canvas.sim.test` | `GET /api/lti/security/jwks`; `GET` and `POST /api/lti/authorize_redirect` | Checks `client_id` (a known simulated key), `redirect_uri` = `{PUBLIC_LTI_URL}/lti/launch/cogniate` exactly, `response_type=id_token`, `scope=openid`, `state`, `nonce`, and that `login_hint` and `lti_message_hint` are the values it sent. Then it answers an auto-submit form that POSTs `id_token` and `state` to `redirect_uri`. The token comes from the scenario of that `login_hint`. Canvas scenarios always use `document_target: "iframe"` (F-CV-17) unless a test sets otherwise on purpose. |
| `school-a.canvas.sim.test`, `school-b.canvas.sim.test` | `POST /login/oauth2/token`; AGS `/api/lti/courses/{c}/line_items` (`GET`, `POST`), `…/line_items/{id}` (`GET`, `PUT`, `DELETE`), `…/scores` (`POST`), `…/results` (`GET`); NRPS `/api/lti/courses/{c}/names_and_roles`; DL return `POST /courses/{c}/deep_linking_response`; a frame page `GET /__frame?url=` that frames a launch URL | Token: verifies the client assertion with `{PUBLIC_LTI_URL}/lti/keys/cogniate` (signature, `iss = sub` = client id, `aud` = this URL, `exp`, unique `jti`) and records the `aud` form (string or array). AGS and NRPS: need its bearer token; record method, path, headers (without the token value) and body; a scenario can make the score POST answer `422` or `400` (F-CV-19). DL return: verifies the response JWT with the tool JWKS (`iss`, `aud`, `deployment_id`, `message_type`, `version`, `nonce`, `iat`, `exp`, echoed `data`) and records the content items. |
| `canvas.school-a.sim.test` | DL return `POST /courses/{c}/deep_linking_response`; frame page `GET /__frame?url=` | A Canvas page host that differs from the service host (F-CV-18, AC-M1-32). No token, AGS or NRPS here. |
| `developer.blackboard.sim.test` | `GET /api/v1/management/applications/{clientId}/jwks.json`; `GET /api/v1/gateway/oidcauth`; `POST /api/v1/gateway/oauth2/jwttoken` | As the Canvas auth and token endpoints. One token per client id for every Learn site. |
| `learn-a.blackboard.sim.test`, `learn-b.blackboard.sim.test` | AGS `/learn/api/v1/lti/courses/{c}/lineItems…`; NRPS `/learn/api/v1/lti/external/namesandroles/{c}`; DL return `POST /webapps/blackboard/controller/lti/v2/deeplinking` | As Canvas sites. The DL return also requires `sub` in the response JWT (F-BB-8). |
| `canvas-self.sim.test` | all Canvas paths above on one origin | Self-hosted Canvas: issuer `https://canvas-self.sim.test`. |
| `lms-sim.test` | control API `/__sim/*` | Only for the tests: set a scenario (claims, roles, deployment, URLs, extra claims, score answer) per `login_hint`; read recorded requests; reset. The service never calls this host. |

A scenario can produce each case of M1: unknown, inactive or wrong deployment, off-site or split-origin URL claims, personal and custom claims, roles (including `…/lti/system/person#TestUser`), missing `client_id`, `422` and `400` score answers. Same input → same token content (except `iat`, `exp`, `nonce`, `jti`).

Production profile values are checked only as constants (AC-M1-01, AC-M1-02 and the Author's unit tests). No test calls a real vendor host.

## 4. Acceptance criteria for M3

- **AC-M3-01** Every AC-M1 criterion has a row in `docs/reviews/M1/qa.md` with PASS or FAIL, the test id, the command, the artifact path and the label `SIM` (AC-M1-23 and AC-M1-30: `MOODLE-LIVE`). Two full runs on the same SHA give the same result per test.
- **AC-M3-02** Moodle regression on the final M1+M2 SHA, `default` profile, no knobs, `simulation_profiles: []`: all 15 T7 criteria PASS in three consecutive runs (QA-E2E); the T2a to T6 acceptance suites PASS (QA). Tests may change only for these approved reasons, each listed with the test id: the portal label changes of M2; the two new Integrations cards; the new `/healthz` field `simulation_profiles`; the role rule (ADR-011 §10: an enrolled site admin who is only a student is now graded); the platform `422` mapping. Any other change needs a new Lead approval.
- **AC-M3-03** Every AC-M2 criterion has a row in `docs/reviews/M2/qa.md` (label `SIM`), with screenshots of each wizard step.
- **AC-M3-04** Simulator hygiene: no private key file in git or in `tests/fixtures`; keys exist only in memory; the simulator log has no token, assertion, approval code or key; `git status` after a run shows no new tracked file.
- **AC-M3-05** The live matrix (§5) is in `docs/reviews/M3/live.md`. Every row has status `PASS`, `FAIL` or `UNVERIFIED`, the label, the environment fields of §2 and the authorization reference. A row is `PASS` only with live evidence of its own label. Without authorization every row is `UNVERIFIED`, with the exact steps.
- **AC-M3-06** Isolation of runs: QA and QA-E2E use the project prefixes, ports and subnets of the phase plan, at most two stacks at once. The baseline containers and the seven existing Docker volumes are unchanged after the run. No Docker Desktop setting changes. No public tunnel, no deployment, no third-party sign-up, no change to a real tenant without written authorization.
- **AC-M3-07** Secrets: QA greps all captured secrets (ltiks, service keys, access tokens from the simulator, client assertions, approval codes) in `infra/.logs/*.jsonl`, the simulator log and the evidence; zero hits (T2b method).

## 6. QA run order

1. QA builds the simulator and the M1 tests from this spec, before reading any M1 code.
2. QA runs M1a criteria on the M1a SHA, then all M1 criteria on the M1 SHA.
3. QA-E2E runs M2 criteria on the merged M1+M2 SHA.
4. QA-E2E and QA run the Moodle regression (AC-M3-02) on the final SHA.
5. QA-E2E records the live matrix.

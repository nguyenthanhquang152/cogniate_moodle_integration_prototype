## Goal

The LTI service and the Cogniate app accept Canvas and Blackboard registrations, launches, Deep Linking and grade return through fixed provider profiles. Every new Canvas or Blackboard binding needs a redeemed operator approval grant. Moodle behaves as before.

## Design notes

- `standard` code paths keep their current outputs. A rule for "profiles other than `standard`" or "shared platforms" must not run for `standard`. The reserved-issuer rule is the only new `standard` refusal.
- Profile values are data. Do not branch on LMS names in launch code; read profile flags (`serviceOriginCheck`, `minimizeClaims`, `deepLinkingResponseSub`, `clientAssertionAudArray`, sharing mode, site URL location).
- The site origin of a launch comes from the stored deployment and platform rows, never from a claim.
- Generation 0 keeps the exact HMAC input of today. Add a unit test that compares a known generation-0 key with the value from the current code.
- Grant redemption: the checks and the redeeming mark (and the Blackboard reservation) happen in one `BEGIN IMMEDIATE` transaction; the LTI call happens after it; the redeemed mark and the connection change happen in a second transaction. Do not hold a database transaction open during the LTI call.
- The app never sends `PATCH /api/platforms/:id` or `DELETE /api/platforms/:id` for a shared platform. Add a unit test that fails if such a call is made.
- Error texts: one text table per service, with the LMS name as a parameter. `standard` texts stay byte for byte.

## Acceptance criteria

Evidence label: `SIM` (signed platform simulation, [M3 §3](M3.md#3-signed-platform-simulator)) unless the AC says `MOODLE-LIVE`.

Setup: `acceptance` profile with `lms-sim` running; Thanh's Library (A) and QA Library B (B) from the seed. QA makes the `blackboard-sim` shared platform with client id `qa-bb-app`, unless the AC says otherwise. Grants come from the AC-named command `docker compose exec cogniate-app npm run app:grant -w services/cogniate-app -- …` on QA's own project.

"Bind A to `dA`" means: A makes a pending Blackboard connection (`blackboard-sim`, site `https://learn-a.blackboard.sim.test`); QA issues a grant for it (`--site https://learn-a.blackboard.sim.test --client-id qa-bb-app --deployment-id dA`); A sends `PUT …/platform {deploymentId: "dA", grantCode}`. "Bind B to `dB`" is the same with `learn-b`. In M1a runs, before the app part exists, QA may bind with `POST /api/platforms/{shared}/deployments` instead (label the row "API setup").

Simulation hosts: `sso.canvas.sim.test` (Canvas auth and JWKS), `school-a.canvas.sim.test`, `school-b.canvas.sim.test` (Canvas account domains: site and service), `canvas.school-a.sim.test` (a Canvas page host that differs from the service host, AC-M1-32), `canvas-self.sim.test` (self-hosted Canvas), `developer.blackboard.sim.test` (Blackboard gateway), `learn-a.blackboard.sim.test`, `learn-b.blackboard.sim.test` (Learn sites).

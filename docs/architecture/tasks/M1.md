Owner: Author (Claude Code Opus 5.5, xhigh). Depends on: M0 (this design) after the design gate. Design: [ADR-011](../adr/ADR-011-multi-lms.md). ## Goal

The LTI service and the Cogniate app accept Canvas and Blackboard registrations, launches, Deep Linking and grade return through fixed provider profiles. Every new Canvas or Blackboard binding needs a redeemed operator approval grant, and the operator can contain a wrong binding. Moodle behaves as before.

## Design notes

- `standard` code paths keep their current outputs. A rule for "profiles other than `standard`" or "shared platforms" must not run for `standard`. The new `standard` refusals are only: reserved issuers, and check 14 for Canvas- or Blackboard-signed launches.
- Profile values are data. Do not branch on LMS names in launch code; read profile flags (`serviceOriginCheck`, `minimizeClaims`, `deepLinkingResponseSub`, `clientAssertionAudArray`, `productFamily`, sharing mode, site URL location).
- The site and service origins of a launch come from the stored deployment and platform rows, never from a claim.
- Generation 0 keeps the exact HMAC input of today. Add a unit test that compares a known generation-0 key with the value from the current code.
- Grant redemption: phase 1 and phase 2 are separate `BEGIN IMMEDIATE` transactions; do not hold a transaction open during the LTI call. Phase 2 and the cleanup of the attempt fields check the attempt id. Every app switch-off, delete or take-over of a Canvas or Blackboard LTI record sends `ifBindingRef` with a ref of the same connection; never rely on a read in the app as the fence.
- The app never sends `PATCH` or `DELETE` for a shared platform. Add a unit test that fails if such a call is made. `app:binding release` deletes only exclusive platforms.
- Error texts: one text table per service, with the LMS name as a parameter. `standard` texts stay byte for byte.

## Acceptance criteria

Evidence label: `SIM` (signed platform simulation, [M3 §3](M3.md#3-signed-platform-simulator-and-transport-gate)) unless the AC says `MOODLE-LIVE`.

Setup: `acceptance` profile with `lms-sim` and `lti-gate` running; Thanh's Library (A) and QA Library B (B) from the seed. QA makes the `blackboard-sim` shared platform with client id `qa-bb-app`, unless the AC says otherwise. Grants come from the AC-named command `docker compose exec cogniate-app npm run app:grant -w services/cogniate-app -- …`, binding commands from `… app:binding …`, on QA's own project.

"Bind A to `dA`" means: A makes a pending Blackboard connection (`blackboard-sim`, site `https://learn-a.blackboard.sim.test`); QA issues a grant for it (`--library <A> --site https://learn-a.blackboard.sim.test --client-id qa-bb-app --deployment-id dA`); A sends `PUT …/platform {deploymentId: "dA", grantCode}`. "Bind B to `dB`" is the same with `learn-b`. In a partial M1a run, QA may bind with `POST /api/platforms/{shared}/deployments` instead (label the row "API setup, partial").

Simulation hosts: `sso.canvas.sim.test` (Canvas auth and JWKS), `school-a.canvas.sim.test`, `school-b.canvas.sim.test` (Canvas account domains: site and service), `canvas.school-a.sim.test` (a Canvas page host that differs from the service host), `canvas-self.sim.test` (self-hosted Canvas issuer and site), `api.canvas-self.sim.test` (its separate service host), `developer.blackboard.sim.test` (Blackboard gateway), `learn-a.blackboard.sim.test`, `learn-b.blackboard.sim.test` (Learn sites).

Grade fixtures (QA): HTML and SCORM paths; completed 7/10, failed 0/100, incomplete (no POST), and the best-score sequence 80 → 60 → 90. Use a fresh resource link per independent grade case.
